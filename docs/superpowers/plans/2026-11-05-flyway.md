# Flyway Migrations (`aritti.flyway`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An OpenIDEA plugin that checks Flyway migration file names and duplicate versions, copies the next migration version, runs Flyway commands in a terminal, and completes placeholders and Flyway config keys.

**Architecture:** Text only, no database. Config is read from `flyway.toml`/`flyway.conf` and Spring `application*` files: locations, naming, placeholder names. Locations become `find_files` globs. A pure check over the file list makes diagnostics, and they're published on `file-opened`/`file-saved` and by a command. CLI commands run through `host::open_terminal`. One `completion` provider covers SQL placeholders and keys in `flyway.conf`/`flyway.toml`.

**Tech Stack:** Rust 2024, `openidea-plugin` SDK `v0.1.37` (`wasm32-wasip2`), shared crate `crates/spring-text` (path dependency) for `.properties`/YAML keys and `project_of`.

**Spec:** this document (section *Scope*). The inputs are public Flyway docs: the naming rules, the Flyway namespace settings list, the default placeholders (`documentation.red-gate.com/fd/flyway-placeholders-namespace-277579022.html`) and the locations setting (`documentation.red-gate.com/fd/flyway-locations-setting-277579008.html`), plus the Spring Boot metadata already in `plugins/spring-boot/data/boot-properties.tsv`.

## Review Focus

- A multi-module project where each module has its own `src/main/resources/db/migration/V1__init.sql`: no duplicate-version error across modules (Task 3 `duplicates_stay_within_a_module`).
- Callback scripts (`beforeMigrate.sql`, `afterMigrate__seed.sql`) and non-migration files (`README.md`, `V1__x.sql.conf`) in a location: no warning (Task 1 `skips_callbacks_and_other_files`).
- Versions written differently but equal to Flyway (`V1_1` and `V1.1`, `V01` and `V1`, `V1.0` and `V1`) are duplicates. `V2` with `U2`, and `V2` with `B2`, are not (Task 1 `equal_versions_share_a_key`, Task 3 `reports_duplicate_versions_and_repeatables`).
- Build output copies (`target/classes/db/migration/...`) aren't scanned as a second location (Task 2 `finds_migrations_from_the_project_config`).
- A project without Flyway: `.sql` files outside the locations (`src/main/resources/schema.sql`) are never flagged, and opening a Java file does no scan (Task 4 `publishes_problems_when_a_migration_opens`, `ignores_files_that_are_not_migrations_or_config`).

## Scope

**In:**
1. **Migration name check** (warning). This covers files with a configured suffix (default `.sql`) under a migration location. It reports a missing `__` separator, a missing or invalid version (`\d+([._]\d+)*`), a repeatable migration with a version, and an unknown prefix (defaults `V`, `U`, `R`, `B`). Callbacks (`before*`/`after*`) are skipped. Naming comes from the project's Flyway config (`sqlMigrationPrefix`, `undoSqlMigrationPrefix`, `repeatableSqlMigrationPrefix`, `baselineMigrationPrefix`, `sqlMigrationSeparator`, `sqlMigrationSuffixes`, and their `spring.flyway.*` forms), not from plugin settings. The project already defines them, and reading them avoids a second place to configure.
2. **Duplicate check** (error). Two versioned, two undo or two baseline migrations with an equal version, or two repeatables with the same description, in the same module.
3. **Locations**: `flyway.locations` in `flyway.toml`, `flyway.conf`, `conf/flyway.toml` and `conf/flyway.conf`, and `spring.flyway.locations` in `**/src/main/resources/application*.{properties,yml,yaml}`. `classpath:`/no prefix, `filesystem:` and `{vendor}` are handled; `s3:`/`gcs:` are skipped. With nothing configured: `classpath:db/migration`, plus `filesystem:sql` (the CLI default) when a Flyway config file exists. The plugin setting `locations` overrides all of this.
4. **Check Migrations** command: publishes problems for every migration and notifies a summary.
5. **Copy Next Migration Version** command: the highest `V`/`B` version with its last part bumped (`V3__`), copied to the clipboard. The notification names the directory. Plugins can't create files.
6. **Flyway commands** `info`, `validate`, `migrate`, `repair`, `clean` in a terminal tab (`host::open_terminal`), with the `flyway` CLI or `mvn flyway:<goal>` (setting `runner`) and extra arguments (setting `arguments`). `clean` runs only when invoked twice within 30 s, and the first call warns.
7. **Completion**: `${` in SQL suggests Flyway's 8 default placeholders plus the project's placeholder names. `flyway.` keys in `flyway*.conf`, and keys under `[flyway]` and `[environments.*]` in `flyway*.toml`.

**Dropped:**
- `spring.flyway.*` completion: `aritti.spring-boot` already completes all 80 keys from its bundled metadata (`plugins/spring-boot/data/boot-properties.tsv:1374-1453`).
- "Rename to …" quick fix for a bad name: code actions can't rename files (LIMITATIONS.md, Symfony › *Code actions can't create, rename or delete files*).
- New-migration file template: `fileTemplates` can't prefill a computed file name, so the clipboard command covers it.
- Gradle tasks (`./gradlew flywayMigrate`) and `./mvnw`: a `process:` capability must be a program name or an absolute path; relative paths are refused (`crates/ide-extension/src/capability.rs:155-159` upstream). Global `gradle` is rare.
- Schema history / `info` tree view, and parsing `-outputType=json`: the terminal shows `info`. Add a view when someone asks.
- Undefined-placeholder warnings: placeholders also come from env vars and CLI args, so they would be false positives.
- `undo`, `baseline`, `check`, `diff` commands: Teams-only or rarely run from an IDE. `-cleanDisabled` overrides: never override Flyway's own safety.
- Navigation and line markers: nothing meaningful to link without a database.

mod tests {
    use super::*;

    fn migration(kind: Kind, version: &str, description: &str) -> Name {
        Name::Migration { kind, version: version.into(), description: description.into() }
    }

    #[test]
    fn parses_versioned_undo_baseline_and_repeatable() {
        let n = Naming::default();
        assert_eq!(parse("V1_1__add_users.sql", &n), migration(Kind::Versioned, "1_1", "add_users"));
        assert_eq!(parse("U2__drop.sql", &n), migration(Kind::Undo, "2", "drop"));
        assert_eq!(parse("B3__baseline.sql", &n), migration(Kind::Baseline, "3", "baseline"));
        assert_eq!(parse("R__views.sql", &n), migration(Kind::Repeatable, "", "views"));
        assert_eq!(parse("V4.sql", &n), migration(Kind::Versioned, "4", ""));
    }

    #[test]
    fn explains_names_flyway_skips() {
        let n = Naming::default();
        let msg = |name: &str| match parse(name, &n) {
            Name::Invalid(m) => m,
            other => panic!("{name}: {other:?}"),
        };
        let unknown = "Flyway skips this file: migration names start with V, U, R or B, like V1__add_users.sql.";
        assert_eq!(msg("V1_init.sql"), "Flyway skips this file: no `__` between the version and the description, like V1__add_users.sql.");
        assert_eq!(msg("V1a__init.sql"), "Flyway skips this file: `1a` isn't a version (numbers separated by dots or underscores).");
        assert_eq!(msg("V1..2__init.sql"), "Flyway skips this file: `1..2` isn't a version (numbers separated by dots or underscores).");
        assert_eq!(msg("V__init.sql"), "Flyway skips this file: the version is missing, like V1__add_users.sql.");
        assert_eq!(msg("R1__views.sql"), "Flyway skips this file: repeatable migrations have no version, like R__refresh_views.sql.");
        assert_eq!(msg("init.sql"), unknown);
        assert_eq!(msg("v1__init.sql"), unknown);
        assert_eq!(msg("Views.sql"), unknown);
    }

    #[test]
    fn skips_callbacks_and_other_files() {
        let n = Naming::default();
        assert_eq!(parse("beforeMigrate.sql", &n), Name::Callback);
        assert_eq!(parse("afterMigrate__seed.sql", &n), Name::Callback);
        assert_eq!(parse("README.md", &n), Name::NotMigration);
        assert_eq!(parse("V1__x.sql.conf", &n), Name::NotMigration);
    }

    #[test]
    fn uses_configured_naming() {
        let n = Naming { versioned: "M".into(), separator: "-".into(), suffixes: vec![".pgsql".into()], ..Naming::default() };
        assert_eq!(parse("M7-add.pgsql", &n), migration(Kind::Versioned, "7", "add"));
        assert_eq!(parse("V7__add.sql", &n), Name::NotMigration);

- [ ] **Step 5: Implement `naming.rs`**

- `parse` order of checks:
  1. No configured suffix ends the name → `NotMigration`.
  2. The stem (name without suffix) starts with `before` or `after` → `Callback`. Add a `// ponytail:` comment: a prefix test, not Flyway's event list.
  3. Match prefixes longest first.
  4. Repeatable: the stem must continue with the separator directly; text before the separator → repeatable-has-version message.
  5. V/U/B: split at the first separator. Without a separator, the rest is a valid version → description `""`; the rest doesn't start with a digit → unknown-prefix message; otherwise → no-separator message. With a separator, an empty version → missing-version message and an invalid one → not-a-version message.
  6. No prefix matches → unknown-prefix message.
- Messages interpolate the configured `versioned`, `undo`, `repeatable`, `baseline` prefixes, the `separator` and the first suffix, exactly as in the tests.
- `version_key`: split on `.` and `_`, trim leading zeros from each part (`"0"` stays `"0"`), drop trailing `"0"` parts.
- `next_version`: pick the highest by numeric comparison of parts (compare `version_key` parts by length, then lexically). Increment the last written part as a decimal string, keeping its width (`0099` → `0100`) and the separators as written. With no versions → `"1"`.
